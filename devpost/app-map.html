WAVEFRONT / PROJECT MAP

How the timing demo works

WAVEFRONT helps beginners explore why two virtual speakers can reach listeners at different times. Coordinates drive a simplified geometric model; one timing snapshot then feeds both browser audio scheduling and the visible arrival markers.

One action, one timing snapshot

The two audio sources are virtual and mix through one browser output. The map animation may be slowed for legibility, but timing values are not.

Reference route through the code

This is a reference route, not a live code tour. Open each stop to trace the behavior.

1. The selected position becomes a timing snapshot

Start at src/App.tsx: selectListener retains the applied correction and switches the idle view, while play requests a snapshot for the current listener and playback version.

2. Coordinates calculate arrivals and alignment

venue.ts holds the 20 m by 12 m room and fixed coordinates. geometry.ts calculates Euclidean distances and arrivals; timing.ts applies the emission correction and freezes the resulting snapshot.

3. Audio and visuals consume that same snapshot

PlaybackController.play schedules both copies of the generated buffer from snapshot offsets. VenueMap draws the paths and wavefront, while ArrivalTimeline positions markers from the snapshot's final arrivals.

A practice to reuse

Separate a risky calculation from the interface, test it against concrete expected values, and then verify the real-world behavior independently. In this project, geometry and timing tests cover the 22.07 ms L1 correction and the +32.87 ms L3 trade-off; the listener's hands-on audio test separately established that the modeled gap was perceptible on their setup.
